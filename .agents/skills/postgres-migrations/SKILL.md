# Postgres migrations (always ≥ T2)

## Golden rule: expand → migrate → contract
Never make a change that breaks the currently-running code. Deploys overlap; old pods run against the new schema.
1. **Expand** — add new nullable column / new table / new index. Deploy.
2. **Migrate** — code writes both, backfill in batches, code reads new. Deploy.
3. **Contract** — drop old column/constraint in a *later* release. (Drops are T3.)

## Safe vs dangerous
| Safe (T2) | Dangerous (T3 or split) |
|---|---|
| add nullable column | add NOT NULL column without default on big table |
| add column with constant default (PG ≥ 11) | change column type (rewrites table) |
| `CREATE INDEX CONCURRENTLY` | `CREATE INDEX` without CONCURRENTLY on hot table |
| add FK `NOT VALID`, then `VALIDATE CONSTRAINT` | add FK validated in one step on big table |
| add CHECK `NOT VALID` then validate | rename column/table used by running code |
| new table | DROP COLUMN / DROP TABLE / TRUNCATE |

## Alembic rules
- `make migration m="add device last_seen_at"`, then **read and edit** the autogenerated file — autogenerate is a draft.
- One concern per revision. Descriptive message. Both `upgrade()` and `downgrade()` implemented (downgrade may raise for irreversible ones — say so).
- Concurrent index: wrap with `with op.get_context().autocommit_block():` and `postgresql_concurrently=True`.
- Set `lock_timeout` (e.g. `SET lock_timeout = '3s'`) at the top of migrations touching hot tables.
- No data backfills inside schema migrations for big tables — write a batched, resumable, idempotent job (1–5k rows per batch, with progress logging).
- Test: `alembic upgrade head` on a fresh DB in CI, plus `downgrade -1 && upgrade head` round-trip.

## Design note must state
table sizes (rows), expected lock types and duration, expand/contract stage, backfill runtime estimate, rollback.
